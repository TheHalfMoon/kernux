# Support

Kernux is under active pre-release development. Support channels are intended to produce reproducible, actionable repository work; they do not imply a response-time SLA.

## Choose the right channel

- **Bug:** use the Bug Report issue form with an exact commit/version, environment, reproduction steps, expected behavior, actual behavior, and redacted evidence.
- **Feature or product proposal:** use the Feature Request form and describe the user outcome before prescribing architecture.
- **Setup or usage question:** use the Support Question form after checking `README.md` and `docs/DEVELOPMENT.md`.
- **Security vulnerability:** follow `SECURITY.md` and do not disclose vulnerability details publicly.
- **Contribution process:** read `CONTRIBUTING.md` and `docs/governance/REPOSITORY_GOVERNANCE.md`.

## What to include

Prefer exact repository revisions, commands, platform/runtime details, minimal reproductions, and bounded logs. Remove credentials, tokens, private keys, personal data, PHI, proprietary content, and unrelated environment details before posting.

## What support cannot override

An issue, comment, or support response cannot authorize work that conflicts with `specs/CURRENT.md`, dependency order, security policy, donor provenance, or required evidence gates.

The repository may close duplicates, unactionable reports, unsupported requests, or items outside the current project frontier while preserving useful evidence for later planning.
